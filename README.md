## 📑 Deliverables Index & Summary

### 1. Requirements Documentation

Defines the foundational behaviors and constraints of the course project:

- **Functional Requirements (FR):** Describes the core operational features, authentication logic, and domain rules that the application must support.
- **Non-Functional Requirements (NFR):** Establishes quality attributes and constraints, including performance criteria (less than 2 seconds of response time), security, usability, and scalability.

### 2. User Stories & Acceptance Criteria

Describes the system's expected functionality from the perspective of its different user roles:

- **User Roles:** Identifies the key application roles, including end-users, administrators, and managers.
- **User Stories:** Expresses requirements using the standard agile format: *As a [role], I want to [action] so that [benefit].*
- **Acceptance Criteria:** Defines the conditions that must be satisfied for each user story to be considered complete.
- **Gherkin Notation:** Structures acceptance criteria using *Given / When / Then* to describe scenarios and expected behavior.

### 3. User Story Mapping & Release Planning

Organizes and prioritizes user stories according to user activities, workflows, and planned project iterations:

- **Release 1 (MVP):** Identifies the essential features planned for the Minimum Viable Product.
- **Release 2:** Organizes additional functionality planned for a subsequent release.
- **Future Iterations:** Identifies further improvements and functionality considered for later development stages.

## 📑 Deliverables Index & Summary

### 1. System Domain

Defines the system context, its environment, the actors who interact with it, and the business rules governing its operation:

- **System Context:** Identifies the system scope, its environment, and its interactions with external entities.
- **Actor Characterization:** Describes the actors who interact with the system, including their roles and involvement in the application's processes.
- **Business Rules:** Establishes the policies, constraints, and conditions that govern the application's behavior.

### 2. CRC Cards

Identifies the main classes in the system and documents their responsibilities and collaborations using Class-Responsibility-Collaborator (CRC) cards:

- **Classes:** Identifies the principal classes representing the application's domain concepts.
- **Responsibilities:** Specifies the tasks and duties assigned to each class.
- **Collaborators:** Identifies the other classes with which each class interacts to fulfill its responsibilities.
- **CRC Card Representation:** Presents one card per class in a table or diagram format.

### 3. Class Diagram

Represents the static structure of the system using UML class diagrams:

- **Classes and Attributes:** Defines the principal classes and the data maintained by each class.
- **Methods:** Describes the operations and behaviors provided by each class.
- **Relationships:** Illustrates the associations and other relationships between classes, clarifying how the system's elements are connected.


### 4. Relational Database Model

Defines the relational database schema required to store and manage application data:

- **Tables:** Identifies the tables used to represent the system's data entities.
- **Primary Keys:** Defines the identifiers used to uniquely identify records.
- **Foreign Keys:** Establishes references between related tables.
- **Relationships:** Illustrates the connections between data entities and supports referential integrity.
- **Model Representation:** Presents the database design as an entity-relationship (ER) diagram or through table definitions.

### 5. Mockups and Wireframes

Presents visual representations of the application's main screens to communicate the proposed user interface and user experience:

- **Screen Designs:** Illustrates the layout and organization of the main application screens.
- **Screen Purpose:** Explains the functionality and objective of each screen.
- **User Interaction:** Communicates how users interact with the proposed interface and navigate the application.
- **Design Tools:** Supports digital mockups created with tools such as Figma or Balsamiq, as well as hand-drawn sketches.

### 6. Business Model Processes

Documents at least one core business process using a UML activity diagram or Business Process Model and Notation (BPMN):

- **Process Flow:** Illustrates the sequence of activities, decisions, and transitions within the business process.
- **Business Logic:** Describes the main steps and interactions involved in carrying out the process.
- **Application Role:** Explains how the process supports the application's business objectives and operational workflows.
- **Process Modeling:** Uses activity diagrams or BPMN notation to represent the process clearly.

### 7. Architecture Diagram

Illustrates the overall software architecture and the interactions between the system's main components:

- **System Components:** Identifies the principal modules, services, and components of the application.
- **Technologies and Layers:** Indicates the technologies used and the architectural layers that organize the system.
- **Communication Flows:** Shows how the components interact and exchange information.
- **Architectural Structure:** Provides an overview of how the system's components fit together to support the application's functionality.
